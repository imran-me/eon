Current System — What's Already Built
Good news: The core payment scheduling engine is already implemented. The payment_schedules table, model, controller, routes, and view all exist. The overdue auto-detection command (schedules:mark-overdue) is also ready. The gaps are: general-purpose (ad-hoc) scheduling and journal/opening-balance integration.

Gap Analysis — Three New Flows to Build

Flow A — Supplier Payable (Opening Balance)

  • JournalEntry (type: opening_balance) saves rows but does NOT create PaymentSchedule
  • Need: JournalController store() → auto-creates schedule when row has due_date + party
  • schedulable_type = JournalEntry, type = 'pay'
  • Once linked, full approve/reschedule/paid flow works

Flow B — Customer Receivable (Opening Balance)

  • Same gap — customer AR opening entries have no schedule
  • JournalController → auto-creates schedule, type = 'receive'
  • schedulable_type = JournalEntry, party_type = 'customer'
  • Full flow works once linked

Flow C — Ad-hoc / Any Purpose

  • No way to schedule "office rent", "ISP bill", "govt fee" not tied to a document
  • New form: party_name (free text), purpose, amount, date — no parent doc
  • schedulable_type = NULL, add nullable source label field
  • Same approve/reschedule/paid flow applies

Controller Change — storeAdHoc()

// Add new method in PaymentScheduleController
public function storeAdHoc(Request $request)
{
    $request->validate([
        'type'           => 'required|in:pay,receive',
        'party_name'     => 'required|string|max:200',
        'party_type'     => 'required|string|max:50',
        'source_label'   => 'required|string|max:200',
        'amount'         => 'required|numeric|min:0.01',
        'scheduled_date' => 'required|date',
        'note'           => 'nullable|string|max:500',
    ]);

    PaymentSchedule::create([
        'schedulable_type' => null,  // no parent doc
        'schedulable_id'   => null,
        'type'             => $request->type,
        'party_type'       => $request->party_type,
        'party_id'         => null,
        'party_name'       => $request->party_name,
        'source_label'     => $request->source_label,
        'amount'           => $request->amount,
        'scheduled_date'   => $request->scheduled_date,
        'status'           => 'pending',
        'note'             => $request->note,
        'created_by'       => auth()->id(),
    ]);

    return back()->with('success', 'Schedule created.');
}

JournalController::store() Change

// After $journalEntry is saved, in the items loop:
foreach ($request->items as $item) {
    JournalItem::create([...]);

    // ← NEW: auto-schedule if opening balance row has due_date
    if (
        $request->source === 'opening_balance' &&
        ! empty($item['due_date']) &&
        ! empty($item['party_type']) &&
        ! empty($item['party_name'])
    ) {
        PaymentSchedule::create([
            'schedulable_type' => JournalEntry::class,
            'schedulable_id'   => $journalEntry->id,
            'type'    => $item['account_type'] === 'liability'
                           ? 'pay' : 'receive',
            'party_type'       => $item['party_type'],
            'party_id'         => $item['party_id'] ?? null,
            'party_name'       => $item['party_name'],
            'source_label'     => $item['reference'] ?? null,
            'amount'           => $item['credit'] ?: $item['debit'],
            'scheduled_date'   => $item['due_date'],
            'status'           => 'pending',
            'created_by'       => auth()->id(),
        ]);
    }
}

Complete System Flow — All Entry Points

After all three phases are complete, payment schedules can come from 5 entry points. All share the same status lifecycle and dashboard.

Entry Point 1 — Sale (Customer Invoice)

Sale created → accountant schedules part/full due amount with date → type = receive → party = customer. Amount cannot exceed sale's due_amount. Marking paid reduces sale.due_amount and sets payment_status = partial/paid.

Built
Entry Point 2 — Purchase (Supplier Bill)

Purchase created → accountant schedules payment installments → type = pay → party = supplier. Also works for TicketPurchase (vendor payable).

Built
Entry Point 3 — Opening Balance Journal (Supplier Payable / Customer Receivable)

JournalEntry (source = opening_balance) saved with per-row due_date → auto-creates PaymentSchedule linked to JournalEntry. Handles existing AP/AR balances that were entered before the schedule system existed.

Phase 2
Entry Point 4 — Ad-hoc (Any Purpose, Any Party)

Manual schedule creation from the PaymentSchedule page — no parent document. schedulable_type = null. Use for: office rent, electricity bill, ISP charges, loan instalments, government taxes, service provider payments, advance to employee, custom receivable from anyone.

Phase 1
Entry Point 5 — Ticket Sale / Ticket Purchase

Same as Entry Points 1 & 2 but for the travel/ticketing module. TicketSale → receive from agent. TicketPurchase → pay to vendor. Already supported in the existing controller.

Built
